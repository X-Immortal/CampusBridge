## 2. 说明

以下详细用例按“核心业务闭环”编写，一个详细用例可覆盖多个系统用例编号。其余 UC 通过系统用例清单、用例图和需求追踪矩阵共同保持闭环。

## 3. 详细用例一：发布需求并匹配帮助者

- 用例编号：UC-03 + UC-05
- 主要参与者：求助者
- 次要参与者：帮助者、平台管理员
- 前置条件：
  1. 求助者已注册并完成校内认证。
  2. 求助者具备发布任务权限。
- 触发条件：求助者产生互助需求，准备在平台发单。
- 后置条件：
  1. 任务成功发布并进入待接单或待审核状态。
  2. 系统按条件向潜在帮助者展示该任务。

**基本流：**

1. 求助者进入发布页面，选择任务分类。
2. 求助者填写任务标题、说明、校区/地点、截止时间、奖励方式和完成标准。
3. 求助者设置沟通偏好、接触偏好和是否要求完成凭证。
4. 系统校验必填项后生成任务。
5. 系统根据分类、校区、时间和标签向相关帮助者展示该任务。
6. 求助者查看浏览情况或候选申请者，进一步按信用、历史记录、距离等条件筛选。
7. 任务进入待接单或已匹配状态。

**替代流：**

1. 若任务属于“出勤/签到协助”等高风险类别，系统不直接公开展示，而是进入管理员审核。
2. 若求助者缺少必要字段，系统阻止发布并提示补全。
3. 若在设定时间内无人响应，系统提示求助者修改任务、延长期限或取消任务。
4. 若求助者中途不再需要帮助，可将任务取消并结束流程。

## 4. 详细用例二：接单与站内沟通

- 用例编号：UC-06 + UC-07
- 主要参与者：帮助者
- 次要参与者：求助者
- 前置条件：
  1. 任务已公开或已通过审核。
  2. 帮助者已完成认证，并满足该任务的接单条件。
- 触发条件：帮助者在平台上看到目标任务并决定参与。
- 后置条件：
  1. 求助者选定一名帮助者，任务进入 `ACCEPTED`，其他待处理申请自动拒绝。
  2. 帮助者显式开始任务后，任务进入 `IN_PROGRESS`。
  3. 双方可以从任务详情进入按用户复用的站内私信，会话保留本次任务的来源上下文。

**基本流：**

1. 帮助者浏览或搜索任务，并使用筛选条件缩小范围。
2. 帮助者查看任务详情，判断是否符合自身时间、能力与校区条件。
3. 帮助者填写申请留言并提交接单申请，申请状态为 `PENDING`；系统通知求助者。
4. 求助者查看候选帮助者的昵称、认证状态、信用、历史记录、标签和申请留言。
5. 求助者选择一名帮助者；系统将任务置为 `ACCEPTED`、接受该申请、拒绝其余待处理申请，并通知相关帮助者。
6. 被选中的帮助者确认开始执行，任务由 `ACCEPTED` 进入 `IN_PROGRESS`。
7. 双方可从任务详情打开站内私信，沟通交付方式、完成时间和注意事项；同一对用户复用已有私信，任务仅作为进入来源。

**替代流：**

1. 帮助者在申请尚未被选择时可以撤回申请，申请变为 `WITHDRAWN`，任务仍保持 `OPEN`。
2. 求助者选择一名帮助者后，其他 `PENDING` 申请自动变为 `REJECTED`，任务不再接受新申请。
3. 在 `ACCEPTED` 或 `IN_PROGRESS` 阶段，双方可按取消规则填写原因并退出，任务恢复为 `OPEN`；进行中退出会记录违约并扣减积分。
4. 私信按双方用户身份唯一复用；从不同任务或帖子进入同一联系人时不会创建重复会话。
5. “仅站内沟通”作为任务偏好展示；当前版本通过站内私信提供沟通渠道，不把联系方式交换作为完成流程的前置条件。

## 5. 详细用例三：完成确认、评价与争议处理

- 用例编号：UC-09 + UC-10 + UC-12 + UC-13 + UC-15
- 主要参与者：帮助者、求助者
- 次要参与者：平台管理员
- 前置条件：
  1. 任务处于进行中状态。
  2. 双方已完成必要沟通。
- 触发条件：帮助者认为任务已完成。
- 后置条件：
  1. 任务变为已完成或争议中。
  2. 完成后触发结算与双向评价。

**基本流：**

1. 帮助者提交完成说明及必要凭证。
2. 系统将任务状态改为待确认，并通知求助者核验。
3. 求助者查看凭证与任务结果。
4. 若结果符合预期，求助者确认完成。
5. 系统执行积分或报酬结算。
6. 系统邀请双方互评，并据此更新信用记录。
7. 任务正式关闭。

**替代流：**

1. 若求助者认为结果不符合要求，可驳回并要求补充说明或重新执行。
2. 若双方就结果产生分歧，可发起举报/申诉，任务转入争议中状态。
3. 管理员基于站内沟通、时间戳、凭证和双方陈述进行仲裁。
4. 若帮助者失联、爽约或提交虚假凭证，管理员可直接触发处罚并更新信用记录。
5. 若求助者迟迟不确认，可触发提醒；达到超时规则后，系统按预设规则进入自动流转或管理员处理。

## 6. 详细用例四：敏感任务审核与违规任务拦截

- 用例编号：UC-14 + UC-16
- 主要参与者：平台管理员
- 次要参与者：求助者
- 前置条件：
  1. 求助者已提交一条新任务。
  2. 系统已完成基础字段校验。
- 触发条件：任务命中敏感分类或内容审核规则。
- 后置条件：
  1. 违规任务被拦截、驳回或转入处罚流程。
  2. 敏感但可讨论的任务进入人工审核。

**基本流：**

1. 求助者提交任务后，系统先检查分类、关键词和基础规则。
2. 若系统识别为敏感任务，则任务进入待审核状态，不直接公开展示。
3. 管理员查看任务说明、风险告知、原因说明和用户认证状态。
4. 管理员决定通过、驳回或要求补充信息。
5. 若审核通过，任务进入正常的待接单流程。

**替代流：**

1. 若任务涉及违法内容、作弊、代考、虚假交易等明确违规行为，系统直接拦截并记录日志。
2. 若同一用户重复发布违规任务，管理员可追加警告、限权或封禁。
3. 若任务表述模糊但不构成直接违规，管理员可要求求助者修改后重新提交。
