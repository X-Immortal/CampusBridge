# CampusBridge 待决事项

**版本：** 1.1 · **更新日期：** 2026-11-16

本文只保存影响业务语义或部署方案的未决选择。决定后更新对应 SRS、架构和契约；代码与既定设计不符的修复项进入[评审记录](reviews/backend-review-2026-11-07.md)，不以“待决”为由悬置工程缺陷。

## 1. 账号字段与验证码防滥用

**关联：** SRS 第 3 节，架构第 8 节。

注册、改密及账号修改需要一致的服务端字段约束。用户名、手机号唯一，邮箱可重复；这些已有规则继续适用。尚需确定：

- 用户名的字符集合、最短和最长长度，以及是否允许后续修改。
- 注册与修改密码统一采用何种长度和强度规则；不能只在改密时检查最短长度。
- 注册手机号与修改手机号是否采用同一格式，普通邮箱的格式及长度约束。
- 同一邮箱、账号和 IP 的发送间隔、周期上限、错误次数及暂时锁定时长。

建议先采用与课程系统规模相称的单实例限制；具体数值需明确后写入规格。声明式输入校验、验证码单次消费和不回传校验哈希属于既定工程要求。

## 2. 刷新令牌与设备撤销

**关联：** SRS FR-AUTH-04，架构第 8.1 节。

登录签发两种用途的令牌，但现有接口只提供登录取得访问令牌。可选择：

| 方案 | 使用流程 | 影响 |
| --- | --- | --- |
| 保持到期重新登录 | 到期提示登录，明确刷新令牌的兼容及后续移除安排 | 流程简单，需要同步客户端和响应契约 |
| 增加刷新能力 | 使用刷新令牌换取访问令牌，并定义轮换、重复使用和撤销规则 | 增加服务端会话/撤销状态及测试范围 |

改密后是否注销全部设备、是否提供“退出全部设备”、退出当前客户端是否同时撤销其服务端凭据，也需统一决定。账号禁用和角色变化按当前数据库信息生效，不在此重复讨论。

## 3. 敏感信息与文件生命周期

**关联：** SRS NFR-SEC-01、FR-FILE-01，架构第 8.2 节。

目标是保护手机号、实名、学号及私密认证/履约材料。待选择的是具体实现与运维策略：

| 决策 | 需要明确的内容 |
| --- | --- |
| 敏感字段保护 | 加密位置、密钥来源、轮换方式及检索/查重方式 |
| 文件访问 | 各用途的公开/私有等级；私有桶、签名 URL 或后端代理的选择及有效期 |
| 临时文件 | 未绑定资源的保留时间、清理触发与失败重试 |
| 外部写入失败补偿 | OSS 成功但元数据失败时立即删除、重试或登记补偿 |
| 删除与留存 | 帖子删除、任务结束、认证撤回后材料保留多久，哪些记录需继续追溯 |

元数据权限与文件字节权限应一起设计。列名包含 cipher、页面不显示 URL，都不能替代访问控制和加密方案。

## 4. 任务截止、重发和旧申请

**关联：** SRS FR-TASK-03/05、第 6.3 节。

取消任务重发沿用原编号，但截止时间、申请唯一性及旧履约记录需要一致的周期规则。

1. **重发前修订：** 是否允许在重发请求中确认新的截止时间及内容，或允许取消任务先编辑再重发。过期时间不能绕过正式发布校验。
2. **旧申请资格：** ACCEPTED/REJECTED 申请是否保持终态、重置为可再次申请，或为新发布周期建立新申请。历史申请应可追溯。
3. **截止与宽限：** 达到 deadline 后立即停止新申请/选人，还是在超时提醒后的宽限期内仍接受操作。提醒与最终取消是两个时间点，必须给出统一业务含义。

建议将重发视为新的发布周期并保留历史；是否继续复用 taskId，以及如何表达周期，应在确定用户流程后选择最小数据模型。不可只解除唯一键而失去原申请和履约关系。

## 5. 争议、送审与统一动作语义

**关联：** SRS 第 6 节和第 9 节。

需要确定：

- 已选人但未开始的 ACCEPTED 任务，能否从专用履约入口直接发起争议；参与者举报触发争议的规则应与之协调。
- 取消、退出、驳回和争议原因采用统一的长度上限，还是按业务动作分别定义。相同动作的重复 HTTP 入口应执行同一规则。
- 是否启用任务发布送审，哪些条件进入 PENDING_REVIEW；关键词命中是否始终直接拒绝。
- 争议裁决是否增加责任认定、理由和证据。当前规格采用 dismiss 正常结算、punish 扣接单者 20 分且不奖励；如调整责任对象或报酬规则，须明确完整裁决流程。

举报处理的默认 -10 分与任务争议裁决的 -20 分属于不同动作。同一事件是否允许两条路径分别处罚，也需在裁决规则中明确。

## 6. 学生证自动审核

**关联：** SRS FR-VERIFY-03，架构第 8.2 节。

人工审核是认证基线。若引入 OCR 自动通过，需要先决定学号、姓名、学校的匹配要求、缺失字段与模糊匹配的处理，以及失败后是否要求补材料或转人工。

候选方案为“仅提供识别结果辅助管理员”或“满足明确条件时自动通过，其余转人工”。自动通过会直接影响任务发布资格，不能仅因为已有 OCR 客户端代码就启用。外部服务的数据保留、费用、超时和重试策略随方案确定。

## 7. 任务发布附件

**关联：** SRS 第 5.1 节与 FR-FILE-01。

正式任务发布暂不接收附件。若扩展，需要确认用途、数量和格式，以及游客、申请者、参与双方分别可见的范围；删除、取消和重发后的材料归属与留存同步确定。数据库已有 TASK 用途枚举不构成启用该功能的决定。

## 8. 草稿同步体验

**关联：** SRS FR-TASK-02。

草稿应能保存不完整输入、补全并发布，这是基线能力。待决定的是进一步的同步体验：手动保存还是自动保存、是否支持跨设备恢复、冲突时保留哪份编辑，以及长期未发布草稿是否清理。

建议先以显式保存和明确成功反馈完成服务端流程，再决定自动保存和版本冲突机制。前端仍保留旧限制、编辑字段不完整等问题属于实现差距，见评审。

## 9. 部署与运行目标

**关联：** SRS NFR-RUN-01，架构第 2、6、8 节。

需要确定课程演示的使用人数与并发量、允许的接口响应时间，并据此选择部署容量。

部署参数包括 TLS 终止与 API 入口、数据库和 OSS 权限、健康检查及演示数据初始化方式。单实例是架构基线；如要求多实例，需另行设计注册/改邮箱验证码共享与调度协调。真实 SMTP、OSS 及目标服务器接入验收属于交付验证，不由本地单元测试结果代替。
