# 数据库设计说明

## 1. 设计目标

本数据库设计用于支撑校园互助服务平台的用户、帖子、任务、对话、附件和治理等核心功能。

数据库设计遵循以下原则：

- `Post` 和 `Task` 分别建模，不使用一个大 `requests` 表承载所有需求。
- `Post` 用于打听求助、二手交易、组队搭子、校园交友等社区型内容。
- `Task` 用于跑腿、委托代办等任务/订单型需求，并完整支持接单申请、状态流转、完成凭证和双向评价。
- `ContentItemView`、`TaskDetailView`、`PostDetailView`、`UserHomepageView` 等为展示对象，不单独建表。
- 附件、举报等跨模块对象采用多态关联，保持后续扩展能力。

## 2. 核心表划分

### 2.1 用户与身份模块

| 表名 | 职责 |
|---|---|
| `users` | 用户登录账号、密码哈希、角色、账号状态 |
| `user_profiles` | 用户公开资料，如昵称、简介、校区、头像、标签 |
| `campus_verifications` | 校内身份认证记录 |
| `user_credits` | 用户当前积分和等级 |
| `credit_records` | 积分变动流水 |

`users` 只保存账号身份的核心数据；用户主动展示的信息放在 `user_profiles`；校内认证中的真实姓名、学号等敏感信息放在 `campus_verifications`；积分结果和积分流水拆分为 `user_credits` 与 `credit_records`。

这种拆分避免 `users` 表承担过多职责，也能清晰表达账号、资料、认证、积分之间的边界。

### 2.2 帖子模块

| 表名 | 职责 |
|---|---|
| `posts` | 社区型需求帖子 |
| `replies` | 帖子回复，支持楼中楼 |
| `post_interactions` | 用户对帖子或回复的点赞、标记 |

`posts.category` 支持以下帖子分类：

```text
INQUIRY_HELP, SECOND_HAND, TEAM_FRIEND, CAMPUS_SOCIAL
```

`posts.status` 支持以下帖子状态：

```text
DRAFT, PUBLISHED, PENDING_REVIEW, HIDDEN, CLOSED, DELETED, REJECTED
```

`accepted_reply_id` 用于支持“采纳回复”功能。由于它引用的是同模块后创建的 `replies`，本设计没有建立物理外键，而是由业务层在采纳时校验回复是否属于当前帖子。

### 2.3 任务/订单模块

| 表名 | 职责 |
|---|---|
| `tasks` | 任务/订单型需求主表 |
| `task_applications` | 接单申请 |
| `completion_proofs` | 完成凭证 |
| `task_histories` | 任务状态流转历史 |
| `reviews` | 任务完成后的双向评价 |

`tasks` 包含任务分类、校区、地点、截止时间、奖励方式、完成标准、是否要求凭证、联系约束和风险确认等字段。

任务状态包括：

```text
DRAFT, OPEN, PENDING_REVIEW, ACCEPTED, IN_PROGRESS,
PENDING_CONFIRMATION, COMPLETED, REVIEWED, CANCELLED, DISPUTED, REJECTED
```

主流程为：

```text
OPEN -> ACCEPTED -> IN_PROGRESS -> PENDING_CONFIRMATION -> COMPLETED -> REVIEWED
```

异常流程包括取消、争议、审核驳回等。状态变化由 `task_histories` 记录，包含 `from_status`、`to_status`、`operator_id` 和 `note`，用于满足 P3 对完整状态机和状态追踪的要求。

### 2.4 对话通知模块

| 表名 | 职责 |
|---|---|
| `conversations` | 站内会话 |
| `messages` | 会话消息 |

`conversations` 支持三类会话：

```text
PRIVATE, SYSTEM, TASK
```

当前业务中的用户沟通统一落在 `PRIVATE` 会话：每个用户分别持有一条面向对方的会话记录，并通过生成列 `private_peer_id` 及唯一索引 `uk_conversations_private_peer(owner_id, private_peer_id)` 保证同一联系人只保留一个可回复私信。`related_type` 和 `related_id` 仅记录从帖子或任务进入私信时的来源上下文，不参与区分会话。`SYSTEM` 用于不可回复的任务和帖子通知；`TASK` 保留为兼容类型，当前接单流程不再按任务编号创建独立会话。

`replyable` 用于区分可回复私信和不可回复系统通知。由于 MySQL 唯一索引允许多个 `NULL`，生成列仅对可回复的 `PRIVATE` 会话返回 `peer_user_id`，不会影响系统通知的多条存储。

`messages.type` 支持：

```text
TEXT, IMAGE, SYSTEM_NOTIFICATION
```

消息附件不直接存入 `messages`，而是通过 `attachments` 的多态关联保存。

### 2.5 附件模块

| 表名 | 职责 |
|---|---|
| `attachments` | 统一保存帖子、回复、任务、完成凭证、消息、举报中的附件 |

附件上传采用“两阶段绑定”：

1. 用户先通过 `/attachments` 上传文件，生成 `TEMPORARY` 状态的附件记录。
2. 发帖、回复、发任务、提交完成凭证或发送消息时传入 `attachmentIds`。
3. 后端校验附件属于当前用户，再将 `owner_type`、`owner_id` 写入附件表并改为 `BOUND`。

`owner_type` 可取：

```text
POST, REPLY, TASK, COMPLETION_PROOF, MESSAGE, REPORT
```

由于这是多态关联，数据库不建立物理外键，避免附件表与所有业务表强耦合；一致性由应用层根据 `owner_type` 分派校验。

### 2.6 治理模块

| 表名 | 职责 |
|---|---|
| `reports` | 用户举报或申诉 |
| `moderation_records` | 管理员处理记录 |

举报目标通过 `target_type` 和 `target_id` 表示，支持举报帖子、回复、任务、用户和消息。治理记录可以关联某条举报，也可以直接记录管理员对某个目标对象的处理。

## 3. 实体关系说明

### 3.1 一对一关系

| 关系 | 说明 |
|---|---|
| `users` 1:1 `user_profiles` | 一个用户对应一份公开资料 |
| `users` 1:1 `user_credits` | 一个用户对应一份当前积分等级 |
| `tasks` 1:0..1 `completion_proofs` | 一个任务最多有一份完成凭证 |

### 3.2 一对多关系

| 关系 | 说明 |
|---|---|
| `users` 1:N `posts` | 用户可以发布多篇帖子 |
| `posts` 1:N `replies` | 帖子可以有多条回复 |
| `replies` 1:N `replies` | 回复支持父子回复 |
| `users` 1:N `tasks` | 用户可以发布多个任务 |
| `tasks` 1:N `task_applications` | 任务可以收到多个接单申请 |
| `tasks` 1:N `task_histories` | 任务会产生多条状态历史 |
| `tasks` 1:N `reviews` | 任务完成后可产生双方评价 |
| `conversations` 1:N `messages` | 一个会话包含多条消息 |
| `reports` 1:N `moderation_records` | 一个举报可以产生多条处理记录 |

### 3.3 多对多关系

| 关系 | 中间表 | 说明 |
|---|---|---|
| `users` N:M `posts` / `replies` | `post_interactions` | 一个用户可以点赞或标记多个帖子/回复，一个帖子或回复也可以被多个用户互动 |
| `users` N:M `tasks` | `task_applications` | 一个用户可以申请多个任务，一个任务也可以收到多个用户的接单申请 |

多对多关系不直接在两个实体表之间建立外键，而是通过中间表保存关联记录及其业务属性。例如 `post_interactions.type` 表示点赞或标记，`task_applications.status` 表示申请状态。

### 3.4 多态关联

| 表 | 多态字段 | 说明 |
|---|---|---|
| `attachments` | `owner_type`, `owner_id` | 附件可属于帖子、回复、任务、凭证、消息、举报 |
| `reports` | `target_type`, `target_id` | 举报对象可为帖子、回复、任务、用户、消息 |
| `moderation_records` | `target_type`, `target_id` | 管理员处理对象可为多种内容 |
| `post_interactions` | `target_type`, `target_id` | 互动对象可为帖子或回复 |

这些多态关系不建立物理外键，原因是它们面向多个目标表。如果强行拆成多套附件表、举报表或互动表，会造成重复结构并降低扩展性。目标对象的一致性校验由应用层根据类型分派完成。

## 5. 隐私数据处理

### 5.1 密码

`users.password_hash` 只保存密码哈希，不保存明文密码。实际实现中应使用 BCrypt、Argon2 或 PBKDF2 等带盐哈希算法。

### 5.2 手机号

手机号不直接明文入库，而是拆成：

| 字段 | 用途 |
|---|---|
| `phone_cipher` | 加密后的手机号，用于必要时展示或联系 |
| `phone_hash` | 手机号哈希，用于唯一性校验和登录查重 |

这样既能支持业务查询，又避免在索引中暴露明文手机号。

### 5.3 校园认证信息

真实姓名和学号属于敏感数据，因此设计为：

| 字段 | 用途 |
|---|---|
| `real_name_cipher` | 真实姓名密文 |
| `student_number_cipher` | 学号密文 |
| `student_number_hash` | 学号哈希，用于查重 |

认证材料地址 `evidence_url` 应只对审核流程开放，普通用户主页只展示 `verified` 等摘要信息。

### 5.4 公开资料

`user_profiles.contact_info` 是用户主动公开的联系方式，不等同于注册手机号。前端展示时应由用户自行控制是否填写。

## 7. 小结

本数据库设计覆盖 P3 要求的核心实体、主键、外键、关系和索引说明。设计重点包括任务状态机、任务历史、接单申请、完成凭证、双向评价、附件上传、站内会话和隐私字段处理，能够支撑系统核心业务流程。
