## 2. AI 助力分析（Q1）

本阶段 AI 最大的贡献是：快速把 P1、P2 中分散的需求、架构约束和课程要求转化为结构化详细设计材料。尤其在类图、API、数据库表之间的对照检查中，AI 能够较快发现“类设计提到但 API 或数据库未覆盖”的缺口，例如个人主页、站内会话、附件上传、点赞标记、采纳回复和任务状态历史等。

估计节省时间：约 6-8 小时。

## 3. AI 误导分析（Q2）

SOLID 检查中发现的 AI 设计问题数量：14。

最严重的设计问题是：AI 原始设计将打听求助、二手交易、组队交友、跑腿代办等需求统一建模为 `Task`，导致 `Task` 类同时承担社区内容、任务订单、状态流转和多类业务字段解释，违反单一职责原则，并使新增内容类型时容易违反开闭原则。

发现的 AI 输出问题：

- 问题1：原始类设计过度任务化。如何发现：团队讨论发现交友、二手、打听求助等内容更接近帖子和回复，不应强制套用接单状态机。如何修正：最终设计拆分为 `Post` 和 `Task`，再通过 `ContentItemView` 统一展示。
- 问题2：原始类图关系表达不清。如何发现：最初类图箭头交叉严重，且颜色和模块边界无法稳定表达设计意图。如何修正：改用手写 PNG 绘制总览类图和分模块类图，明确关联、聚合、组合、实现和依赖关系。
- 问题3：API 初稿对异常和权限覆盖不足。如何发现：对照 P3 要求和核心类设计时，发现初稿缺少常见错误响应、状态冲突、权限失败、附件上传、私聊创建等接口。如何修正：在 OpenAPI 中补充 400、401、403、404、409、422、500 等错误响应，并补全会话、附件、互动和个人主页接口。
- 问题4：数据库初稿与类设计存在不一致。如何发现：对照 `Post`、`Task`、`Conversation`、`Message`、`Attachment` 等类时，发现部分字段和关系没有完全对应。如何修正：调整 `schema.sql`、ER 图和数据库设计说明，使表结构覆盖核心类和 API schema。

## 4. Prompt 改进计划（Q3）

上阶段改进措施的验证结果：P2 阶段提出的“提供课程约束、团队规模、现有技术栈、已完成文档和不做项”仍然有效。与直接要求 AI 生成设计相比，提供 P1、P2 文档路径、P3 检查表和明确交付格式后，AI 输出更容易进入可审查、可修改的状态。

本阶段新的改进措施：

- 在要求 AI 生成类图或 API 前，先明确“哪些模型是核心模型，哪些只是展示对象或扩展对象”，避免 AI 把所有需求合并成单一大类。
- 对 AI 生成的设计不直接采用，而是按 SOLID、P3 接口覆盖、数据库字段覆盖、P2 架构一致性四个维度逐项检查。
- 对图形类交付物，应在 Prompt 中明确要求模块颜色、关系符号、箭头避让和可读性，不只要求“生成类图”。
- 对最终提交物，应增加“更新相对路径、统一命名口径、检查旧文件引用”的收尾检查。

## 5. 本阶段的核心工程判断

决策内容：将系统核心内容模型从“所有需求都是任务”调整为“`Post` 和 `Task` 分别建模，使用 `ContentItemView` 统一展示”。其中 `Post` 承载打听求助、二手交易、组队搭子、校园交友等社区型内容，`Task` 承载跑腿、代办等需要接单、完成确认和双向评价的任务型内容。

为什么 AI 无法做这个决策：该决策不仅是类名或字段设计问题，还涉及产品形态、用户心智、课程要求、任务状态机覆盖、后续扩展和实现成本之间的取舍。AI 可以提出若干建模方案，但无法替团队判断哪些需求应保持社区式灵活性，哪些需求必须进入任务状态机，也无法替团队承担最终设计复杂度与可实现性的平衡。
