## 1. 引言

### 1.1 目的

本文档用于定义“校园互助服务平台”的正式需求，作为后续原型设计、系统实现、测试验收与阶段评审的依据。文档基于真实问卷和访谈结果整理，AI 输出仅作为辅助参考，不直接替代人工调研结论。

### 1.2 范围

本系统面向大学生校园生活中的互助场景，支持用户在校内发布与承接各类互助需求，包括但不限于：

- 跑腿 / 代取 / 即时事务
- 咨询答疑 / 学习资料共享
- 二手交易 / 失物招领
- 组队协作 / 拼单拼车
- 出勤 / 签到协助等高风险场景

系统重点解决以下问题：

1. 快速找到合适的人。
2. 降低沟通和匹配成本。
3. 保证任务完成可确认、可追溯、可评价。
4. 为纠纷、爽约、隐私泄露和违规任务提供治理机制。

### 1.3 定义与术语

| 术语 | 定义 |
|---|---|
| 求助者 | 在平台上发布需求的一方 |
| 帮助者 | 在平台上承接需求并提供帮助的一方 |
| 任务 | 平台上的一次互助请求或资源互换活动 |
| 敏感任务 | 具有较高合规、责任或争议风险的任务，如出勤/签到协助 |
| 完成凭证 | 任务完成后由帮助者或系统提交的可验证材料，如图片、文字说明、聊天记录摘要 |
| 信用记录 | 由完成次数、评价结果、爽约情况、申诉处理结果共同形成的用户记录 |
| 积分 | 平台内部的非现金激励单位，可用于互助奖励、等级或权益兑换 |

## 2. 总体描述

### 2.1 产品视角

本平台是一个面向校园内部的互助服务系统，核心定位不是“泛社交平台”，而是“面向真实校园需求的可信匹配与任务闭环平台”。系统应优先保证：

- 校内身份可信
- 发布流程简洁
- 匹配与筛选有效
- 沟通尽量留在站内
- 完成确认与纠纷处理闭环清晰

### 2.2 用户特征

| 用户类型 | 特征 | 主要需求 |
|---|---|---|
| 时间紧张型用户 | 忙于实习、上课、活动，强调效率 | 跑腿、代取、应急协助、简流程 |
| 学习互助型用户 | 关注资料、答疑、经验分享 | 资料共享、学习辅导、课程经验 |
| 事务代办型用户 | 更看重可靠性和追责 | 代交材料、借物、证件/流程协助 |
| 即时场景用户 | 需求临时、碎片化、响应时效强 | 顺路帮拿、带药、临时拼单 |
| 管理员 | 负责审核、仲裁和秩序维护 | 内容治理、违规处理、敏感任务审核 |

### 2.3 运行环境

- 面向校内用户使用的 Web 或移动端系统
- 支持文本与图片级别的站内沟通
- 支持任务状态、评价、举报等基础业务闭环

### 2.4 设计约束

1. 第一版必须控制复杂度，优先交付核心互助闭环。
2. 正式需求必须基于真实调研结论，避免被泛化产品模板带偏。
3. 敏感场景不可无条件开放，必须配置额外治理规则。
4. 平台不应依赖重社交、排行榜或复杂运营玩法才能成立。

### 2.5 假设与依赖

1. 用户愿意完成校内身份认证，但前台展示需兼顾隐私保护。
2. 用户接受站内消息作为主要沟通方式。
3. 第一版可先支持积分、协商报酬等轻量激励，不强依赖完整支付体系。
4. 管理员规模有限，因此审核与仲裁流程必须聚焦高风险与争议场景。

| FR-17 | 平台应提供超时处理规则：若一方长时间未响应，系统可根据任务状态触发提醒、自动流转或转入管理员处理。 | 中 | [人工补充] | 用于覆盖爽约、失联和不确认等异常流。 |

## 7. 结论

本需求规格说明书基于真实调研形成，明确了平台第一版应优先满足的核心能力：可信认证、轻量发布、精准筛选、站内沟通、任务闭环、评价信用和治理约束。与 AI 原始输出相比，本版本删除了未经调研支持的重社交和模板化功能，补上了真实使用过程中的异常流、筛选字段与敏感场景边界。
