# CampusBridge 核心类设计重构稿

## 1. 重构背景

经过团队讨论，原先以 `Request` 统一承载所有内容的设计虽然灵活，但容易出现核心类过重、类型详情过多、策略和工厂复杂度偏高的问题。参考实际校园平台的使用方式后，本版设计改为：

```text
统一展示，分别建模。
```

也就是说，首页、板块页、搜索结果、用户点赞/标记列表等位置使用统一的 `ContentItemView` 展示内容；但底层业务模型分为：

```text
Post：社区型内容，采用帖子 + 回复模式。
Task：任务型内容，采用接单 + 状态机模式。
```

这样既能避免任务板块被孤立，又能避免普通帖子被强行塞进任务流程。

## 2. 设计原则

1. `ContentItemView` 只是统一展示对象，不是业务实体。
2. `Post` 和 `Task` 分别建模，避免一个万能类承载所有字段和流程。
3. `Post` 支持打听求助、二手交易、组队&搭子、校园交友等社区型场景，当前阶段不进一步区分字段。
4. `Task` 支持跑腿、代办类场景，必须具备完整状态机、双方确认、历史记录和双向评价。
5. 站内对话与系统通知统一在“会话”模型下展示；系统通知不可回复。
6. 用户主页当前只展示基础资料、认证状态和积分等级，但通过 View Object 保持后续扩展空间。

## 3. P0 覆盖说明

根据 `00-大作业总览.pdf`，MVP 阶段 P0 必须完成三个模块：用户管理、需求发布与浏览、订单流程管理。本设计对它们的覆盖关系如下：

| P0 模块 | 总览要求 | 本设计中的对应 |
|---|---|---|
| 用户管理 | 注册、登录、个人资料 | `User`、`UserProfile`、`AuthService`、`UserProfileService` |
| 需求发布与浏览 | 发布、列表、详情、筛选 | `PostService`、`TaskService`、`ContentQueryService`、`PostQueryService`、`TaskQueryService`、`ContentSearchCriteria`、`PostDetailView`、`TaskDetailView` |
| 订单流程管理 | 完整的接单-完成流程 | `Task`、`TaskApplication`、`TaskStatus`、`CompletionProof`、`TaskHistory`、`TaskService` |

说明：本项目仍保留“帖子和任务分别建模”的设计。课程总览中较宽泛的“需求”在本设计中被拆为两类：社区型需求由 `Post` 表达，任务/订单型需求由 `Task` 表达。课程总览中的“订单流程管理”主要由 `Task` 模块承担。

## 5. 统一展示模块

### 5.1 ContentItemView

**职责：** 表示内容列表中的统一展示项。它可出现在首页、板块页、搜索结果、用户主页、点赞列表、标记列表等场景。

`ContentItemView` 不直接承载业务流程，只负责把不同业务对象以统一卡片形式展示。

| 属性 | 类型 | 说明 |
|---|---|---|
| `itemType` | `ContentItemType` | 来源类型，如帖子或任务 |
| `sourceId` | `Long` | 来源对象 ID |
| `title` | `String` | 展示标题 |
| `summary` | `String` | 内容摘要 |
| `authorId` | `Long` | 作者/发布者 ID |
| `authorName` | `String` | 作者展示名 |
| `categoryName` | `String` | 板块或分类名称 |
| `statusLabel` | `String` | 状态展示文案 |
| `createdAt` | `LocalDateTime` | 创建时间 |
| `sortTime` | `LocalDateTime` | 排序时间 |
| `replyCount` | `Integer` | 回复数，可为空 |
| `likeCount` | `Integer` | 点赞数，可为空 |
| `rewardLabel` | `String` | 奖励展示文案，任务可用 |

### 5.2 PostDetailView

**职责：** 表示帖子详情页展示对象，用于满足 P0 中“需求详情查看”的社区型场景。它组合帖子主体、作者摘要、回复列表和当前用户互动状态，不作为持久化实体。

| 属性 | 类型 | 说明 |
|---|---|---|
| `post` | `Post` | 帖子主体 |
| `authorProfile` | `UserHomepageView` | 作者公开资料摘要 |
| `replies` | `List<Reply>` | 回复列表 |
| `likedByCurrentUser` | `Boolean` | 当前用户是否已点赞 |
| `markedByCurrentUser` | `Boolean` | 当前用户是否已标记 |
| `acceptedReplyId` | `Long` | 被采纳回复 ID，可为空 |

### 5.3 TaskDetailView

**职责：** 表示任务详情页展示对象，用于满足 P0 中“需求详情查看”的任务/订单型场景。它组合任务主体、发布者、接单申请、完成凭证和状态历史等信息。

| 属性 | 类型 | 说明 |
|---|---|---|
| `task` | `Task` | 任务主体 |
| `requesterProfile` | `UserHomepageView` | 需求方资料摘要 |
| `providerProfile` | `UserHomepageView` | 服务方资料摘要，可为空 |
| `applications` | `List<TaskApplication>` | 接单申请列表，仅需求方或管理员可见 |
| `completionProof` | `CompletionProof` | 完成凭证，可为空 |
| `history` | `List<TaskHistory>` | 状态历史 |
| `reviews` | `List<Review>` | 评价列表 |

### 5.4 ContentSearchCriteria

**职责：** 表示内容列表查询和筛选条件，用于首页、板块页、搜索页等场景。它不是业务实体，只是查询参数对象。

| 属性 | 类型 | 说明 |
|---|---|---|
| `keyword` | `String` | 关键词，可为空 |
| `itemTypes` | `Set<ContentItemType>` | 内容类型筛选，可同时包含帖子和任务 |
| `categoryCode` | `String` | 板块或任务分类编码 |
| `campus` | `String` | 校区筛选 |
| `locationKeyword` | `String` | 地点关键词 |
| `status` | `String` | 状态筛选，由查询服务按内容类型解释 |
| `createdAfter` | `LocalDateTime` | 发布时间下限 |
| `createdBefore` | `LocalDateTime` | 发布时间上限 |
| `sortBy` | `String` | 排序字段，如时间、热度、截止时间 |
| `pageRequest` | `PageRequest` | 分页参数 |

说明：`ContentSearchCriteria` 只表达筛选意图，不包含 SQL 或数据库实现细节。`ContentQueryService` 只负责编排统一展示查询，具体的帖子查询和任务查询分别交给 `PostQueryService` 与 `TaskQueryService`，再通过适配器转为 `ContentItemView`。

### 5.5 ContentItemType

```text
POST
TASK
```

### 5.6 ContentItemAdapter<T>

**职责：** 将不同业务对象转换成 `ContentItemView`。该设计体现适配器模式，保证新增内容类型时不需要修改统一展示对象。

该接口使用泛型，避免 `toContentItem(Object source)` 带来的类型安全问题。调用方不应把任意 `Object` 传给适配器，而应根据 `sourceType()` 或明确的查询分支分派给对应适配器。

| 方法 | 返回值 | 说明 |
|---|---|---|
| `sourceType()` | `Class<T>` | 返回适配器支持的源对象类型 |
| `itemType()` | `ContentItemType` | 返回转换后的展示项类型 |
| `toContentItem(T source)` | `ContentItemView` | 将指定类型对象转换为统一展示项 |

### 5.7 PostContentItemAdapter

**职责：** 将 `Post` 转换为 `ContentItemView`。

| 方法 | 返回值 | 说明 |
|---|---|---|
| `sourceType()` | `Class<Post>` | 返回 `Post` 类型 |
| `itemType()` | `ContentItemType` | 返回 `POST` |
| `toContentItem(Post post)` | `ContentItemView` | 转换帖子展示项 |

### 5.8 TaskContentItemAdapter

**职责：** 将 `Task` 转换为 `ContentItemView`。

| 方法 | 返回值 | 说明 |
|---|---|---|
| `sourceType()` | `Class<Task>` | 返回 `Task` 类型 |
| `itemType()` | `ContentItemType` | 返回 `TASK` |
| `toContentItem(Task task)` | `ContentItemView` | 转换任务展示项 |

## 8. 任务模块

### 8.1 Task

**职责：** 表示跑腿、委托代办等任务型内容。任务具有明确接单、确认、进行中、完成、评价流程。

说明：课程总览中使用“订单流程管理”描述接单到完成的过程。本设计中不额外引入 `Order` 类，而是由 `Task` 承担“订单/需求单”的核心职责，避免在当前规模下形成 `Task` 与 `Order` 的重复建模。

职责边界说明：

1. `Task` 实体只维护自身状态和基础不变量，例如当前状态、需求方、服务方、截止时间、奖励说明等。
2. `Task` 中的状态方法只做单个状态变化本身，不负责权限校验、历史记录、通知发送、积分/信用变化。
3. `TaskService` 负责任务状态机编排，包括权限判断、调用实体状态方法、写入 `TaskHistory`、发送系统通知、触发积分/信用事件等。
4. Controller 不直接修改 `Task.status`，必须通过 `TaskService` 完成状态流转。

主状态机：

5. `REVIEWED` 表示双方完成评价或评价期结束。
6. `CANCELLED` 和 `DISPUTED` 为异常状态。

### 12.3 ContentQueryService

**职责：** 作为统一展示查询的应用层门面。它可用于首页、板块页、搜索结果、点赞列表、标记列表等场景，但不直接实现帖子查询细节、任务查询细节、权限过滤和排序规则。

职责边界说明：

1. `ContentQueryService` 负责接收统一查询请求，并根据 `ContentSearchCriteria.itemTypes` 判断需要查询哪些内容类型。
2. 它将帖子相关查询委托给 `PostQueryService`，将任务相关查询委托给 `TaskQueryService`。
3. 它负责调用对应的 `ContentItemAdapter<T>`，把不同来源对象转换为 `ContentItemView`。
4. 它可以合并不同来源的查询结果，并进行统一分页或展示排序，但具体排序规则应由查询条件或排序策略表达，不写死在该服务中。
5. 它不直接访问 `PostRepository`、`TaskRepository` 的复杂查询方法，避免变成“大查询服务”。

1. `TaskService` 是任务状态机的应用服务入口。
2. 它负责校验操作者身份和权限，例如只有需求方可以确认服务方、只有服务方可以提交完成。

4. 它负责在状态变化后调用 `TaskHistoryService` 记录历史。
5. 它负责触发系统通知，例如接单确认、状态变更、待确认、评价提醒。

## 14. 设计模式与 SOLID 对应

| 设计点 | 使用方式 | 作用 |
|---|---|---|
| 适配器模式 | `ContentItemAdapter<T>` | 将 `Post`、`Task` 转换为统一展示项，使用泛型保证类型安全 |
| 门面模式 | `UserHomepageService` | 聚合资料、认证、积分，避免 `UserProfile` 依赖认证和积分流程 |
| 策略思想 | `CreditLevelPolicy` | 隔离积分等级计算规则 |
| 单一职责 | `Post` 与 `Task` 分离 | 普通社区内容不承担任务状态机，任务也不伪装成帖子 |
| 单一职责 | `Task` 与 `TaskService` 分工 | `Task` 维护自身状态，`TaskService` 负责编排权限、历史、通知和积分/信用事件 |
| 单一职责 | `ContentQueryService` 与 `PostQueryService`、`TaskQueryService` 分工 | 统一展示查询只做编排，具体查询细节下沉到对应内容类型 |
| 接口隔离 | `TaskService` 与 `TaskHistoryService` 分离 | 状态流转和历史查询职责分开 |
| 依赖倒置 | Service 依赖 Repository 接口 | 业务层不依赖具体数据访问实现 |

## 15. 与 P2 架构设计的对应关系

| P2 模块 | 本设计中的对应 |
|---|---|
| 用户认证与档案模块 | `User`、`UserProfile`、`CampusVerification`、`AuthService`、`UserProfileService`、`UserHomepageView` |
| 任务发布与管理模块 | `PostService` 负责社区发布，`TaskService` 负责任务发布 |
| 搜索筛选与匹配模块 | `ContentQueryService` 作为统一展示查询门面，内部依赖 `PostQueryService`、`TaskQueryService` |
| 接单与任务生命周期模块 | `TaskApplication`、`Task`、`TaskStatus`、`TaskHistory` |
| 站内沟通模块 | `Conversation`、`Message` |
| 评价信用模块 | `Review`、`UserCredit`、`CreditRecord` |
| 举报仲裁与治理模块 | `Report`、`ModerationRecord` |
| 通知与审计日志模块 | 系统通知通过 `Conversation` + `Message` 表达，任务历史通过 `TaskHistory` 表达 |

## 16. 后续扩展点

1. 二手交易若变复杂，可从 `PostCategory.SECOND_HAND` 中拆出 `TradeItem`，并新增 `TradeContentItemAdapter`。
2. 组队&搭子若变复杂，可拆出 `TeamActivity`，并新增 `TeamContentItemAdapter`。
3. 首页热榜可以作为独立排序策略或查询规格对象，由 `ContentQueryService` 编排使用，不必进入核心实体。
4. 系统通知若变复杂，可进一步拆出独立 `Notification`，但当前统一在会话中展示。
5. 用户主页后续可展示用户帖子、任务、二手商品、评价摘要等内容。
