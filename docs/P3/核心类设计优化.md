# CampusBridge 核心类设计优化稿

## 1. 优化背景

经过团队讨论，原先以 `Task` 为中心的设计不适合 CampusBridge 的真实定位。校园互助平台不应让用户感觉自己只能“发布任务”和“完成任务”，而应更接近一个面向校园场景的发帖交流平台。

结合 `00-大作业总览.pdf` 中对“发布互助需求”“需求列表浏览”“接单-完成流程”“完整状态机”“双方确认完成”“双向评价”的要求，本版设计采用如下核心原则：

```text
Request 是平台核心内容实体，对应课程要求中的“互助需求”。
Reply 是用户参与需求讨论、回应需求的统一入口。
部分 Reply 可以扩展为需要需求方确认的申请。
TaskExtension 是对明确可承接需求的订单/任务流程扩展，用于落实完整状态机、双方确认和双向评价。
```

换句话说，平台主干是：

```text
用户 -> 发布需求 -> 回复 -> 互动 / 举报 / 个人主页展示
```

可选互助扩展是：

```text
某条回复 -> 申请参与 -> 需求方确认 -> TaskExtension 状态机 -> 双方确认完成 -> 双向评价
```

这一调整保留了“发帖/回复”模型的灵活性，同时用 `Request` 命名回应课程总览中“用户发布需求”的表述，并用 `TaskExtension` 满足课程对完整订单流程的要求。

## 2. 设计范围说明

当前阶段优先设计平台主干能力：

```text
用户认证与档案 -> 用户主页 -> 发布需求 -> 首页分区浏览
-> 搜索/筛选需求 -> 回复交流 -> 点赞/标记 -> 举报治理
```

必须补充设计的课程要求流程：

```text
服务方通过回复申请接单 -> 需求方确认 -> 进行中 -> 服务方提交完成
-> 需求方确认完成 -> 双向评价 -> 积分/信用变化
```

暂缓深入设计的能力包括：完整私信系统、复杂推荐算法、帖子热榜算法、真实支付、积分商城、二手商品独立主页、对象存储、Redis、MQ、Elasticsearch 等。

### 2.1 与课程总览要求的对应关系

| 总览要求 | 本设计中的落点 |
|---|---|
| 发布互助需求 | `Request` |
| 需求分类体系 | `RequestCategory` + `RequestType` |
| 需求列表浏览、详情、筛选 | `RequestQueryService` |
| 接单 | `Reply` + `ReplyApplication` |
| 确认 | 需求方接受 `ReplyApplication`，并创建/进入 `TaskExtension` |
| 进行中 | `TaskStatus.IN_PROGRESS` |
| 完成 | `CompletionProof` + `TaskStatus.PENDING_CONFIRMATION` |
| 双方确认完成机制 | 服务方提交完成，需求方确认完成 |
| 订单历史记录 | `TaskHistory` |
| 双向评分 | 两条 `Review` 记录 |
| 信用分与等级展示 | `UserCredit` + `CreditRecord` |

## 4. 用户与身份模块

### 4.1 User

**职责：** 表示用户账号主体，负责登录身份、角色和账号可用性。用户公开展示信息、积分等级、认证记录不直接塞入该类。

| 属性 | 类型 | 说明 |
|---|---|---|
| `id` | `Long` | 用户唯一标识 |
| `username` | `String` | 登录名 |
| `passwordHash` | `String` | 加密后的密码 |
| `phone` | `String` | 手机号，可选 |
| `email` | `String` | 邮箱，可选 |
| `role` | `UserRole` | 用户角色 |
| `enabled` | `Boolean` | 账号是否可用 |
| `createdAt` | `LocalDateTime` | 创建时间 |
| `updatedAt` | `LocalDateTime` | 更新时间 |

**关键方法：**

| 方法 | 返回值 | 说明 |
|---|---|---|
| `isAdmin()` | `boolean` | 判断是否为管理员 |
| `disable()` | `void` | 禁用账号 |
| `enable()` | `void` | 启用账号 |
| `changePassword(String newPasswordHash)` | `void` | 修改密码哈希 |

### 4.2 UserProfile

**职责：** 表示用户主动维护的公开资料。该类主要保存昵称、头像、校区、标签等相对稳定的信息，不负责积分、等级、信用计算，也不负责认证流程。

说明：用户主页需要展示“是否已认证”，但完整认证流程不应放入 `UserProfile`。认证状态应由 `CampusVerification` 管理，并在查询用户主页时通过 `UserHomepageView` 聚合展示。

| 属性 | 类型 | 说明 |
|---|---|---|
| `id` | `Long` | 档案 ID |
| `userId` | `Long` | 所属用户 ID |
| `nickname` | `String` | 昵称 |
| `bio` | `String` | 个人简介，可选 |
| `campus` | `String` | 常驻校区 |
| `avatarUrl` | `String` | 头像地址 |
| `interestTags` | `List<String>` | 兴趣标签 |
| `skillTags` | `List<String>` | 能力标签 |
| `createdAt` | `LocalDateTime` | 创建时间 |
| `updatedAt` | `LocalDateTime` | 更新时间 |

**关键方法：**

| 方法 | 返回值 | 说明 |
|---|---|---|
| `updateBasicInfo(String nickname, String bio, String campus)` | `void` | 更新公开资料 |
| `updateAvatar(String avatarUrl)` | `void` | 更新头像 |
| `updateTags(List<String> interestTags, List<String> skillTags)` | `void` | 更新标签 |

**职责：** 表示用户主页的展示对象，用于组合公开资料、认证摘要和积分等级。它不是核心持久化实体，而是面向前端展示的 View Object / DTO。

### 4.4 UserCredit

**职责：** 表示用户当前积分和等级。该类由系统奖励、处罚或运营规则更新，用户不能直接修改。

说明：`UserCredit` 只保存用户当前积分与等级结果，不直接决定等级阈值规则。等级计算交给 `CreditLevelPolicy`，避免后续等级规则变化时频繁修改实体类。

## 5. 需求发布模块

### 5.1 Request

**职责：** 表示用户发布的互助需求，是平台最核心的内容实体。它在表现形式上接近帖子，但在课程语境中对应“需求发布与浏览”模块。

`Request` 采用“薄核心”设计，只保存所有需求共有的字段。与类型相关的地点、时间、报酬、价格、人数、失物信息等不直接放入 `Request`，而是放入对应的 `RequestDetail` 扩展对象。

这样可以避免 `Request` 变成充满可选字段的万能类，也能在新增需求类型时减少对核心类的修改。

说明：`replyCount`、`likeCount`、`markCount` 是用于列表展示的冗余统计字段，由回复和互动流程维护。它们不代表 `Request` 直接负责回复或互动逻辑。

| 属性 | 类型 | 说明 |
|---|---|---|
| `id` | `Long` | 需求 ID |
| `authorId` | `Long` | 需求方 ID |
| `categoryId` | `Long` | 所属首页分区或板块 ID |
| `type` | `RequestType` | 需求类型 |
| `title` | `String` | 标题 |
| `content` | `String` | 正文内容 |
| `status` | `RequestStatus` | 需求内容状态 |
| `replyCount` | `Integer` | 回复数 |
| `likeCount` | `Integer` | 点赞数 |
| `markCount` | `Integer` | 标记数 |
| `createdAt` | `LocalDateTime` | 创建时间 |
| `updatedAt` | `LocalDateTime` | 更新时间 |

**关键方法：**

| 方法 | 返回值 | 说明 |
|---|---|---|
| `publish()` | `void` | 发布需求 |
| `hide()` | `void` | 隐藏需求 |
| `close()` | `void` | 关闭需求 |
| `reopen()` | `void` | 重新打开需求 |
| `increaseReplyCount()` | `void` | 增加回复数 |
| `isOpen()` | `boolean` | 判断是否可回复或互动 |
| `isWrittenBy(Long userId)` | `boolean` | 判断用户是否为作者 |

### 5.12 RequestTypePolicy

**职责：** 表示不同需求类型的规则策略。不同 `RequestType` 在创建校验、是否允许申请、是否允许任务扩展、是否允许采纳回复等方面可能不同，应通过策略对象隔离这些差异。

该设计体现策略模式：`Request` 不直接包含各种类型判断，而是由对应的 `RequestTypePolicy` 处理类型相关规则。

说明：该策略只处理需求类型的核心规则，不负责推荐、排序、热榜、通知等其他功能，避免策略接口膨胀。

| `supportsTaskExtension()` | `boolean` | 是否支持任务/订单流程扩展 |
| `supportsAcceptReply()` | `boolean` | 是否支持采纳回复 |

### 5.14 RequestFactory

## 8. 任务扩展模块

### 8.2 TaskStatus

```text
ACCEPTED
IN_PROGRESS
PENDING_CONFIRMATION
COMPLETED
REVIEWED
CANCELLED
DISPUTED
```

说明：

1. 申请是否待接受由 `ReplyApplication` 管理。
2. 需求内容是否开放由 `RequestStatus` 管理。
3. `TaskExtension` 从 `ACCEPTED` 开始，表示需求方已经确认某个服务方。
4. 主状态机为：`ACCEPTED -> IN_PROGRESS -> PENDING_CONFIRMATION -> COMPLETED -> REVIEWED`。
5. 异常流程包括：`CANCELLED`、`DISPUTED`。

主流程解释：

| 状态 | 进入条件 | 说明 |
|---|---|---|
| `ACCEPTED` | 需求方接受某条申请型回复 | 对应课程总览中的“确认” |
| `IN_PROGRESS` | 双方进入实际协作 | 对应“进行中” |
| `PENDING_CONFIRMATION` | 服务方提交完成说明或凭证 | 等待需求方确认 |
| `COMPLETED` | 需求方确认完成 | 双方确认完成机制中的最终确认 |
| `REVIEWED` | 双方完成评价，或评价期结束 | 对应“完成 -> 评价”后的关闭状态 |

## 12. 相比上一版修改稿的主要变化

| 上一版设计 | 本版优化 | 修改理由 |
|---|---|---|
| `Participation` 作为独立参与记录 | 改为 `ReplyApplication` | 申请参与本质上是某些回复的特征，而不是独立于回复的行为 |
| `TaskExtension` 直接绑定需求 | `TaskExtension` 绑定已确认申请 | 任务约束应发生在需求方确认某个申请之后 |
| `Request` 包含大量可选字段 | 改为 `Request` 薄核心 + 多个 `RequestDetail` | 避免万能类和大量空字段，提高可扩展性 |
| 类型差异写在 `Request` 或 Service 判断中 | 增加 `RequestTypePolicy` | 用策略模式隔离不同需求类型的规则 |
| 创建需求和详情的逻辑散落 | 增加 `RequestFactory` + `RequestDetailCreator` | 用工厂模式集中创建 `Request` 和对应详情，并降低工厂对具体详情类的依赖 |
| `UserProfile` 包含信用分 | 拆出 `UserCredit` | 公开资料和系统积分等级的来源、权限、生命周期不同 |
| `UserCredit` 自己决定等级计算 | 增加 `CreditLevelPolicy` | 隔离等级阈值规则，避免积分实体承担规则计算 |
| 用户主页直接从 `UserProfile` 暴露认证信息 | 增加 `UserHomepageView` + `UserHomepageService` | 主页可展示认证状态，但认证流程仍由 `CampusVerification` 独立管理，降低耦合 |
| 认证方式未单独表达 | 增加 `VerificationMethod` | 认证方式和认证状态分离，方便扩展 |
| `Reply.accepted` 作为回复属性 | 用 `InteractionType.ACCEPT` 表达采纳 | 采纳只属于问答场景，不污染通用回复 |
| 点赞、收藏、标记边界不清 | 保留 `LIKE`、`MARK`、`ACCEPT`，暂缓 `FAVORITE` | `MARK` 负责关注更新提醒，收藏暂时价值不清 |
| 完成凭证直接存图片列表 | 凭证材料通过 `Attachment` 关联 | 降低附件处理重复 |
| `TaskExtensionService` 同时处理状态和历史查询 | 拆出 `TaskHistoryService` | 遵守接口隔离，避免任务状态服务膨胀 |

## 13. 后续讨论点

1. `ReplyApplication` 是否应该进入核心类图，还是只作为扩展类出现。
2. `TaskExtension` 是否需要在 P3 第一版详细设计中展开，还是仅说明扩展方向。
3. `InteractionType.ACCEPT` 是否需要限制一个问答类需求只能采纳一个回复。
4. `MARK` 是否需要单独触发通知类，还是只在文档中说明后续可扩展。
5. `CreditRecord.sourceType` 是否应在本阶段改成枚举。
6. 二手交易是否需要 `TradeExtension`，还是当前只用 `RequestType.TRADE` 表达。
7. `UserHomepageView` 是否需要展示用户最近需求，还是只展示资料、认证状态、校区、积分等级。
8. 是否需要对首页热榜建模。当前建议不建模，只作为后续查询/排序策略。
9. `RequestTypePolicy` 是否会在后续承担过多职责，需要持续限制其边界。
