# API 设计 AI 辅助实验

## 1. 实验目的

本实验对应 P3 阶段任务 2.2“AI 辅助实验”。实验先使用 AI 根据前期需求和核心类设计生成一版 API 初稿，再进行人工审查和修改，重点检查接口命名、错误处理、参数校验和安全设计是否完整。

本次实验涉及两个文件：

| 文件 | 说明 |
|---|---|
| `openapi-ai初稿.yaml` | AI 生成的 API 初稿，用于审查对比 |
| `openapi.yaml` | 人工审查、补充和调整后的 API 规范 |

## 2. AI 初稿概况

AI 初稿基本覆盖了用户注册/登录、发布帖子、发布任务、浏览列表、接单、查看订单详情和提交评价等核心接口。整体结构采用 OpenAPI 3.0.3，接口也大体符合 RESTful 风格。

但是，初稿更多是从“功能列表”直接生成接口，对最终领域模型理解不够充分，尤其没有完全体现 `Post` 和 `Task` 分别建模、`ContentItemView` 统一展示、任务状态机、附件独立上传、站内会话等设计。

## 3. 审查发现的问题

### 3.1 接口命名不够一致

AI 初稿中部分任务流程接口使用了动作式路径，例如：

| 初稿接口 | 问题 |
|---|---|
| `POST /tasks/{taskId}/accept` | 直接把“接单”简化为任务动作，没有体现接单申请 |
| `POST /tasks/{taskId}/complete` | 直接完成任务，没有区分提交完成凭证和发布者确认 |

这种写法虽然直观，但会弱化任务流程中的双方确认机制，也不利于后续扩展多个申请人、拒绝申请、撤回申请等功能。

修正版本将任务接单拆为：

| 修改后接口 | 说明 |
|---|---|
| `POST /tasks/{taskId}/applications` | 服务方提交接单申请 |
| `GET /tasks/{taskId}/applications` | 发布者查看候选申请 |
| `POST /tasks/{taskId}/applications/{applicationId}/accept` | 发布者选择帮助者 |

同时将任务状态流转统一为：

| 修改后接口 | 说明 |
|---|---|
| `POST /tasks/{taskId}/completion` | 服务方提交完成凭证 |
| `POST /tasks/{taskId}/status-transitions` | 发布者确认、拒绝、取消或发起争议 |

### 3.2 错误处理不完整

AI 初稿只在少数接口中给出了 `400` 或 `401`，大量接口只有成功响应。这会导致接口文档无法说明常见异常情况，例如未登录、无权限、资源不存在、状态冲突、参数校验失败等。

修正版本为接口补充了常见错误响应：

| 错误码 | 含义 |
|---|---|
| `400` | 请求参数格式错误 |
| `401` | 未认证或登录失效 |
| `403` | 无权限执行操作 |
| `404` | 目标资源不存在 |
| `409` | 状态冲突或重复操作 |
| `422` | 业务校验不通过 |
| `500` | 服务器内部错误 |

同时在 `components.schemas.ErrorCode` 中保留了业务错误码定义，便于后续实现时统一前后端错误处理。

### 3.3 参数校验不完整

AI 初稿中的请求参数大多只写了类型，缺少 `required`、`minLength`、`maxLength`、`minimum`、`maximum`、`enum` 等约束。例如：

| 初稿字段 | 问题 |
|---|---|
| `CreatePostRequest.title` | 没有长度限制 |
| `CreateTaskRequest.deadline` | 只是普通字符串，没有声明 `date-time` 格式 |
| `CreateReviewRequest.rating` | 没有限制评分范围 |
| `category`、`status` | 使用普通字符串，没有枚举约束 |

修正版本补充了更明确的参数校验规则。例如评分限制为 1-5，分页大小限制为 1-100，帖子和任务分类使用枚举，任务截止时间使用 `date-time` 格式。

### 3.4 安全设计不够充分

AI 初稿虽然声明了 Bearer JWT，但没有充分区分哪些接口需要认证，哪些接口可以匿名访问；同时也没有体现私聊、附件、评价等接口中的权限边界。

修正版本保留全局 Bearer JWT 认证，并对注册、登录接口显式设置 `security: []`。对需要权限判断的接口，补充了 `401` 和 `403` 响应，例如修改帖子、接单、确认任务、发送消息、处理举报等接口。

### 3.5 对核心类设计覆盖不足

AI 初稿只覆盖了最基本的用户、帖子、任务和评价，没有覆盖核心类设计中已经确定的若干模块：

| 缺失内容 | 修改后补充 |
|---|---|
| 统一展示对象不清晰 | 使用 `ContentItemView` 支持 `/content` 统一内容流 |
| 用户个人主页缺失 | 新增 `GET /users/{userId}/profile` |
| 站内对话缺失 | 新增会话列表、创建会话、消息列表、发送消息 |
| 附件上传缺失 | 新增 `POST /attachments`，业务接口通过 `attachmentIds` 引用附件 |
| 点赞、标记、采纳回复缺失 | 新增帖子互动和采纳回复接口 |
| 任务状态历史缺失 | 在 `TaskDetailView` 中包含 `TaskHistory` |
| 双向评价表达不足 | `Review` 中保留 `reviewerId` 和 `revieweeId` |

## 4. 修改后的设计结果

修改后的 `openapi.yaml` 保持了 `Post` 和 `Task` 分别建模的结构：

- `Post` 用于打听求助、二手交易、组队搭子、校园交友等社区型内容；
- `Task` 用于跑腿、委托代办等任务/订单型需求；
- `/content` 通过 `ContentItemView` 统一展示帖子和任务；
- `TaskApplication`、`CompletionProof`、`TaskHistory`、`Review` 共同支撑完整任务流程；
- `Conversation` 和 `Message` 支撑站内私聊和系统通知；
- `Attachment` 独立处理附件上传，避免帖子、任务、消息等模块直接耦合文件存储细节。

最终版本已经使用 Redocly 进行校验，校验结果为 API 描述文件有效。

校验结果中仍有一些推荐级 warning，例如缺少 `operationId`、tag 描述、license 字段等。这些问题不影响 OpenAPI 文件有效性，属于文档规范优化项。

## 5. 实验结论

AI 初稿能够较快生成 API 文档骨架，并覆盖主要功能入口，但对复杂业务规则和领域模型边界的把握不足。经过人工审查后，修正版本重点补充了任务状态机、双方确认、错误处理、参数校验、权限控制、附件上传、统一展示和站内会话等内容，使 API 设计更符合 P3 详细设计要求，也更贴合前期核心类设计。

本次实验表明，AI 适合用于快速生成 API 初稿，但最终接口是否合理仍需要结合系统架构、核心类设计和业务流程进行人工判断与修正。
