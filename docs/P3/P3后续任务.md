# P3 后续任务交接说明

请在完成 P3 API 设计、数据库设计前阅读本文档，理解为什么现在采用这样的结构，以及后续任务应该如何沿着这个方向继续做。

## 1. 当前设计的核心判断

目前核心设计已经基本确定为：

**统一展示，分别建模**。

也就是说，首页、板块页、搜索结果、用户点赞/标记列表等地方，可以统一展示不同类型的内容；但是底层业务模型不再用一个万能类承载所有需求，而是拆成两类：

- `Post`：社区型内容，采用帖子 + 回复模式。
- `Task`：任务/订单型内容，采用接单 + 状态机模式。

这个判断是这一阶段最重要的设计决策。

一开始曾经倾向于把校园互助平台里的所有内容都理解为“任务”，但后来发现这样并不合理。校园平台里有些内容确实是任务，比如跑腿、代办；但也有很多内容更接近帖子，比如打听求助、二手交易、组队搭子、校园交友。如果把这些都塞进 `Task`，会导致普通交流也被迫拥有接单、确认、完成、评价等流程，类会越来越重，也不符合真实使用场景。

所以现在的设计是：

```text
Post：打听求助 / 二手交易 / 组队&搭子 / 校园交友
Task：跑腿 / 委托代办
```

同时，为了避免任务板块被孤立，我们设计了 `ContentItemView` 作为统一展示对象。也就是说，`Post` 和 `Task` 虽然底层分开建模，但在首页和列表中可以统一展示。

## 2. P0 功能如何被覆盖

`00-大作业总览.pdf` 中对 P0 的要求主要有三个：

| P0 模块 | 当前设计中的对应 |
|---|---|
| 用户管理 | `User`、`UserProfile`、`AuthService`、`UserProfileService` |
| 需求发布与浏览 | `PostService`、`TaskService`、`ContentQueryService`、`PostQueryService`、`TaskQueryService` |
| 订单流程管理 | `Task`、`TaskApplication`、`TaskStatus`、`TaskHistory`、`CompletionProof`、`Review` |

其中需要特别注意的是，“需求发布”在我们的设计里不是单一接口，而是两类：

- 社区型需求：走 `PostService.publishPost()`
- 任务型需求：走 `TaskService.publishTask()`

“订单流程管理”则主要由 `Task` 模块承担。我们没有额外设计 `Order` 类，而是让 `Task` 承担课程总览中“订单/需求单”的职责。这样可以避免 `Task` 和 `Order` 重复建模。

## 3. 后续 API 设计怎么接

API 设计可以直接从服务接口展开。至少要覆盖 P3 文档要求的六类接口：

| 要求接口 | 建议对应服务 |
|---|---|
| 用户注册 / 登录 | `AuthService.register()`、`AuthService.login()` |
| 发布需求 | `PostService.publishPost()`、`TaskService.publishTask()` |
| 浏览需求列表（含筛选） | `ContentQueryService.listHomeItems()`、`listCategoryItems()`、`searchItems()` |
| 接单 | `TaskService.applyTask()`、`TaskService.acceptApplication()` |
| 查看订单详情 | `TaskService.getTaskDetail()` |
| 提交评价 | `ReviewService.submitReview()` |

API 文档不要只写 URL，还要按 P3 要求写清楚：

- URL 路径
- HTTP 方法
- 请求参数
- 响应格式
- 错误码
- 是否需要登录认证

我建议 API 命名尽量保持 RESTful 风格，例如：

```text
POST /api/auth/register
POST /api/auth/login
POST /api/posts
POST /api/tasks
GET  /api/content
POST /api/tasks/{taskId}/applications
POST /api/tasks/{taskId}/applications/{applicationId}/accept
GET  /api/tasks/{taskId}
POST /api/tasks/{taskId}/reviews
```

这里最容易出错的地方是“发布需求”。不要只设计一个 `/api/requests`，否则又会退回到单一 `Request` 模型。我们现在已经明确：帖子和任务分别建模，但可以统一展示。

## 4. 后续数据库设计

数据库设计需要严格贴合目前的核心类设计。尤其注意不要把我们已经拆开的东西又合并回一个大表。

### 4.1 建议核心表

用户与身份：

```text
users
user_profiles
campus_verifications
user_credits
credit_records
```

帖子模块：

```text
posts
replies
post_interactions
```

任务模块：

```text
tasks
task_applications
completion_proofs
task_histories
reviews
```

对话通知：

```text
conversations
messages
```

附件与治理：

```text
attachments
reports
moderation_records
```

### 4.2 几个必须坚持的数据库原则

第一，`Post` 和 `Task` 要分表。

不要设计一个 `requests` 表，把帖子和任务都放进去，再用大量可空字段区分。这样虽然短期看起来统一，但会让普通帖子字段和任务流程字段混在一起，后续很难维护。

第二，用户账号、资料、认证、积分要分开。

`users` 表只放账号相关信息，例如用户名、密码哈希、手机号、邮箱、角色、启用状态。公开资料放 `user_profiles`，认证记录放 `campus_verifications`，积分等级放 `user_credits`，积分变化放 `credit_records`。

第三，任务状态必须有历史表。

`tasks.status` 只能表示当前状态，不能代替订单历史。课程总览明确要求订单历史记录，所以需要 `task_histories`：

```text
task_id
from_status
to_status
operator_id
note
created_at
```

第四，评价要独立成表。

不要在 `tasks` 表里加 `requester_rating`、`provider_rating`。双向评价应该通过 `reviews` 表表达，两条记录分别表示需求方评价服务方、服务方评价需求方。

第五，附件可以用通用表，但要说明约束。

`attachments` 可以使用：

```text
owner_type
owner_id
```

这种设计灵活，但数据库层面很难对所有类型都建立强外键。所以附件归属对象由应用层根据 `owner_type` 校验。

## 5. 索引设计的方向

索引应该围绕实际查询场景设计，不是越多越好。至少需要考虑：

```text
posts(category_id, status, created_at)
replies(post_id, created_at)
post_interactions(user_id, type)

tasks(category, status, created_at)
tasks(requester_id)
tasks(provider_id)
task_applications(task_id, applicant_id)
task_histories(task_id, created_at)
reviews(task_id)

conversations(owner_id, last_message_at)
messages(conversation_id, created_at)
```

另外，涉及隐私和安全的字段要单独说明：

- `password_hash` 只存哈希，不存明文。
- `phone`、`email` 可考虑脱敏展示。
- `real_name`、`student_number` 只应后台可见。

## 6. 目前设计中需要保持一致的命名

为了避免后续文档互相打架，我建议大家尽量沿用以下命名：

| 概念 | 推荐命名 |
|---|---|
| 统一展示项 | `ContentItemView` |
| 社区帖子 | `Post` |
| 任务/订单型需求 | `Task` |
| 接单申请 | `TaskApplication` |
| 完成凭证 | `CompletionProof` |
| 任务历史 | `TaskHistory` |
| 双向评价 | `Review` |
| 系统通知/私聊 | `Conversation` + `Message` |
| 用户公开资料 | `UserProfile` |
| 校内认证 | `CampusVerification` |
| 积分等级 | `UserCredit` |

不要在 API 或数据库文档里突然改成另一套概念，例如一会儿叫 `Request`，一会儿叫 `Order`，一会儿叫 `TaskOrder`。如果确实要用“订单”这个词，可以在说明里写清楚：本设计中的 `Task` 承担课程总览中“订单/需求单”的职责。
